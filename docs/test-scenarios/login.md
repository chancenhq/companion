# Login/authentication test scenarios

Scope: Companion member-facing mobile authentication in the Rails + Flutter monorepo. This tracker is based on the current code paths in `app/controllers/api/v1/auth_controller.rb`, `app/controllers/sessions_controller.rb`, `app/models/mobile_device.rb`, `app/controllers/api/v1/base_controller.rb`, `mobile/lib/providers/auth_provider.dart`, `mobile/lib/services/auth_service.dart`, `mobile/lib/screens/login_screen.dart`, and `mobile/lib/screens/sso_onboarding_screen.dart`.

Step 4 status: backend characterization is using Minitest. Current relevant backend run: `bin/rails test test/controllers/api/v1/auth_controller_test.rb test/controllers/api/v1/base_controller_test.rb test/controllers/sessions_controller_test.rb` passes with 121 runs, 707 assertions, 0 failures, 0 errors, and 1 pre-existing skip.

Open questions:

- I found no phone-number login, SMS OTP provider, or Kenya/Rwanda/South Africa-specific authentication branch in the member-facing mobile auth code. Country-specific behavior may exist outside this flow, but I did not find it in login/authentication.
- Backend characterization tests should use the existing Minitest style under `test/controllers`/`test/integration`; do not introduce RSpec for Step 4.

Findings to flag:

- Raw user-data debug logging is not development-only. `AuthService#_logRawUserPayload` has no `kDebugMode` or release-build guard, and `LogService` records all log levels into its in-memory list before calling `debugPrint`. The Settings screen exposes the debug log viewer without a `kDebugMode` guard. This means raw mobile user payloads can be retained and copied from production/release builds unless some external build/runtime setting removes this screen.
- The debug-dialog API-key login UI is development-only in the normal login screen. The API-key button, backend URL block, and settings icon on the login screen are all wrapped in `kDebugMode`, so they are not reachable from a production/release build through that UI. The underlying `AuthService.loginWithApiKey` method and stored API-key auth mode still exist, but I found no production login-screen entry point to the dialog.
- I found no explicit failed-login counter or account lockout for repeated email/password or MFA failures. Rack::Attack is enabled in production/staging and applies broad IP-based throttles to `/api/`, but there is no auth-specific throttle or per-account failed-attempt policy for `/api/v1/auth/login`.
- "Already logged in elsewhere" is not a global account/session state in the code read so far. The backend revokes prior active tokens only for the same `MobileDevice` when issuing a new token; tokens for other devices are not revoked by login. In plain terms: yes, the same member can be logged into different device records at the same time. I found no code comment or config proving whether that is intentional product behavior.

| App starts with stored expired OAuth tokens while online | Mandatory | Backend covered by Minitest | Flutter calls `/api/v1/auth/refresh`; backend rotates the token, revokes the old access token, and updates matching device `last_seen_at` if found. |
| App starts with stored expired OAuth tokens while offline or refresh fails | Mandatory | Covered by Flutter test for offline branch | Flutter logs out locally and clears stored auth state when expired stored tokens are found while offline. | API-key login from the debug mobile login dialog | Mandatory | Backend covered by Minitest + Flutter tests | Debug-only UI calls `GET /api/v1/accounts` with `X-Api-Key`; backend API-key auth covers valid, invalid, expired, revoked, insufficient-scope, and deactivated-user cases. Flutter tests cover the debug-build dialog entry point and persisted API-key restore. The visible Flutter API-key login entry point is `kDebugMode`-only, but persisted API-key auth is restored without a release-build guard; logged in `docs/security-backlog.md`. |
| Google mobile SSO succeeds for an already-linked OIDC identity | Mandatory | Covered by Minitest | Flutter opens `/auth/mobile/google_oauth2`; Rails OmniAuth callback issues mobile tokens behind a one-time cache code, deep-links back, and Flutter exchanges the code via `/api/v1/auth/sso_exchange`. |
| Mobile SSO callback has an invalid, expired, missing, or reused authorization code | Mandatory | Covered by Minitest | `/api/v1/auth/sso_exchange` requires a cache code, deletes it atomically before returning tokens, returns `400` when the code param is missing/blank, and returns `401` for invalid/expired/reused codes. |
| Mobile SSO succeeds at provider but identity is not linked | Mandatory | Covered by Minitest | Rails stores a 10-minute linking code and deep-links with `status=account_not_linked`; Flutter shows the SSO onboarding screen for link/create choices. This is account-binding sensitive. |

| SSO onboarding creates a new account from a linking code | Mandatory | Covered by Minitest | `/api/v1/auth/sso_create_account` creates an SSO-only user only when there is a pending invitation or account creation is allowed by JIT/domain config, then links the OIDC identity and issues mobile tokens. |
| Apple Sign-In succeeds for an existing Apple identity | Mandatory | Covered by Minitest | `/api/v1/auth/apple_sign_in` verifies the Apple identity token, finds `OidcIdentity(provider: "apple", uid: sub)`, and issues mobile tokens for that identity's user. |
| Apple Sign-In links to an existing user by verified/provided email | Mandatory | Covered by Minitest | If no Apple identity exists but the Apple token/provided params include an email matching a local user, the backend creates the Apple identity for that user and issues tokens. | Apple Sign-In creates a new SSO user | Mandatory | Covered by Minitest | If there is no Apple identity and no matching local user, backend requires an email, JIT-creates an SSO user, links Apple identity, and issues tokens. |
| Apple Sign-In missing/invalid identity token or missing email for new account | Later | Not started | Missing token returns `400`; verification failure returns `401`; missing email for a new account returns `422`. |
| SSO/Apple/mobile token issuance fails during device registration | Mandatory | Partially covered + backlog finding | Login/signup/Apple invalid-device rejection is covered. A partial-state risk in SSO onboarding token issuance is logged in `docs/security-backlog.md` for follow-up. |
| Authenticated API request uses an invalid, expired, missing-scope, missing-owner, or deactivated-user OAuth token | Mandatory | Covered by Minitest | `Api::V1::BaseController` rejects invalid/expired/missing-scope tokens, missing/deleted users, and deactivated users. This protects account data after login. |
| Member signs up from the mobile login screen | Later | Not started | The login screen exposes sign-up; backend validates password strength, invite-code requirements, invitation/default-family assignment, device info, and token issuance. This is adjacent auth, not returning-member login. |
| Local-login-disabled configuration | Later | Not started | Web session login honors `AuthConfig.local_login_enabled?`; the mobile API login path does not check that flag in the code read so far. Unclear whether mobile local login is expected to ignore this config. |
